## 1. 背景与目标

课堂讲规则时，老师要手工点满 16 个季度才能把一条规则的后果展示出来：慢、容易撞门撞错、讲到第 3 年通常已经下课。现有的"暂停运营"（`isPaused`）只能冻住局面供讲解，不能替老师把局面推下去。

目标：一键让系统按剧本自己走完 4 年，老师在**任意操作步骤**上暂停讲解、单步继续、跳到下一季；学生看到的是真实界面在真实规则门控下变动——包括"这一步是谁按了哪个按钮"。

不是目标：不是给学生的自动代做工具，不是 What-if 推演（roadmap §3 P3，有硬性前置），不做多结局与失败分支示范，不进成绩判定链路。

## 4. 设计

### 4.1 模块边界

新增 5 个文件，每个一个职责，`src/demo/` 除 `runner.ts` 外不 import store：

| 文件 | 职责 | 依赖 |
|---|---|---|
| `src/demo/types.ts` | `YearIntent` / `DemoStep` / `RunnerPhase` 等共享类型 | 无 |
| `src/demo/script.ts` | 4 份年度意图 + 讲解点表（纯数据，老师改这儿） | `types`、`utils/controlTable` 的 `CONTROL_STEPS` |
| `src/demo/decide.ts` | 纯函数 `(state, intent, year, quarter) => DemoStep[]` | `utils/rules`（BOM、单价、加工费） |
| `src/demo/runner.ts` | 逐季展开队列、播放控制、撞门检测 | store 的真实 action |
| `src/components/DemoPanel.tsx` | 右侧抽屉 + 顶部横幅 + 快捷键绑定 | 只读 runner 状态 |

隔离判据（每个单元能否不看内部就被理解和测试）：`decide.ts` 是纯函数，喂状态出步骤；`runner.ts` 只有时序与状态机；`DemoPanel.tsx` 不含任何业务判断；`script.ts` 是数据。

### 4.2 store 改动（3 处，全在 `src/store/enterpriseStore.ts`）

1. 顶层新增两个字段，与 `state`/`saveFiles`/`validationError` 平级：
   ```ts
   demoMode: boolean;                 // 初始 false
   demoSnapshot: EnterpriseState | null;  // 进入演示前的当前进度
   ```
   **为什么不放进 `EnterpriseState`**：`saveGame`/`autoSaveGame` 序列化的是 `state` 整体，逐帧指纹覆盖 `{id,timestamp,version,resetCount,state}`。放进去会污染存档格式、需要 bump `SAVE_FORMAT_VERSION`，并让演示标记进入核对报告与运行控制表的数据源。放在外层，存档包/指纹/控制表三条链路一个字节都不变。
2. `autoSaveGame` 首行 `if (get().demoMode) return;`——掐掉 §3 那条唯一自动落盘路径。
3. `enterDemo()` / `exitDemo()`：进入时 `demoSnapshot = 深拷贝(state)`（沿用 `createFreshState()`，`enterpriseStore.ts:2993`），`state = createFreshState()` 并强制 `isPaused = false`，`demoMode = true`，清 `validationError`；退出时反向恢复并置 `demoMode = false`、`demoSnapshot = null`。

### 4.3 讲解点与规则文案单源

给 `RULE_SECTIONS` 每项加 `id`（纯增字段，`tests/integrityCopy.test.ts` 按 title 查找，不受影响）：
`ad` / `market` / `orders` / `factory` / `production` / `rd-iso` / `finance` / `save` / `cost` / `time`。

讲解点引用到**条目级**：`{ stepId: 'b-2', rule: { section: 'ad', item: 1 } }`。面板只渲染那一条原文加一个「打开规则说明」按钮，不复述、不另写文案——文案仍只有 `RULE_SECTIONS` 一份。代价是 `item` 是位置索引、重排会指错，因此 §6 第 4 组测试断言每个讲解点存在且不越界；讲解点**指错条目比缺讲解更糟**。

### 4.4 剧本：4 份年度意图

```ts
interface YearIntent {
  year: 1 | 2 | 3 | 4;
  adAmount: number;                 // b-2 前置；决定解锁张数（每 1M 解锁 2 张）
  orderCap: number;                 // 选单张数上限，decide 会按在手产能再裁
  newLines: { factoryId: string; type: LineType; product: 'P1'|'P2' }[];  // q-8
  rdP2: boolean;                    // q-15：本年是否推进 P2
  marketInvest: MarketId[];         // e-5：开拓 + 已准入市场的年度维持
  isoInvest: ISOType[];             // e-5
  shortLoanQuarters: number[];      // q-3：哪几季申请短贷（每次 20M）
  sellFactory?: string;             // q-12
  cashPad: number;                  // 安全垫下限，decide 不许把现金压到它下面
}
```

四处与草案不同，每一处都是撞门撞出来的，不是审美调整：

1. **广告 2M 贯穿四年**（草案 2/4/6/4）。订货会的解锁数 `advertisements.period===1` 之和跨年不清零（store:1736-1738），第 3 年起同样的 2M 已能解锁 12 张：按草案的 2/4/6/4 投会在**第 4 年第 2 季**撞门（透支缺口 2M）。只把第 3 年提到 6M 能过，但终局现金从 8M 掉到 5M（权益反而高 3M 到 126M）——多投的广告是把现金曲线换成权益上限，而 §2 的取向是"只要流程完整、不断流"，不追权益最大，故取 2M。`orderCap` 放宽到 6/8/8 则读数与采用值**逐项相同**：真正卡住选单的是产能不是上限。
2. **第 2 年上不了全自动线**：`productionLineLimits.automatic = 2`（store:51-56）而开局两条已在（line-1/line-2），配额从第 1 年起就是 0 剩；引擎对超配额是 `return state` 静默空操作（store:925-932），第一次真跑就在第 2 年第 1 季撞停。同产能（1 件/季）只剩柔性线（24M 原值、现金流 30M），本局曲线接不住，故取半自动（12M 现金流、1 件/2 季）。
3. **第 3 年短贷从一笔变两笔**（Q1 续贷 + Q3 增量）：跨入第 4 年 Q1 那一道关口要 44M 长贷本息 + 21M 短贷本息。逐条隔离过的取值（同一份 runner，只改剧本）：
   - 一条线 + 只 Q1 短贷 → 第 3 年第 4 季被拒，缺口 19M；
   - 一条线 + Q1/Q3 两笔 → **跑通**（采用）；
   - 一条线 + 不借短贷 → 缺口 18M；
   - 两条线 + Q1/Q3 → 缺口 14M（第 2 年的第二条线无论如何都压穿关口）；
   - 第 2 年改借 Q1/Q3 而不是第 3 年 → 缺口 20M（那笔的到期日 abs 11 落在关口之前，等于把洞往前挪）。
   这是 §9-5 后备顺序的**第 1 档**（加大贴现与短贷）；第 2 档（第 2 年多一条线抬高收入）实测反噬，用不了。
   **另一条没过短贷的路**：第 2 年一条线都不上 + 只 Q1 短贷 → 也跑通（终局现金 39M、权益 119M），代价是整局没有"投资新生产线"这一步，q-8 讲解点永不触发，且权益少 4M。本轮取"上一条线 + 多一笔短贷"，因为它保住了 §4.4 第 2 年"扩产能年"的教学环节；这个取舍归用户复核。
4. **第 4 年不申请长贷**：不加也零撞门跑满 16 季（终局现金 8M），加了则终局现金 26M 但挂 20M 长贷 + 2M 全年息，而终局报告无轧差口径，观感是"借了不用还"。代价写在这儿：**讲解点表 12 条里只剩 `e-1`（长贷年末申请、3 年期 10%）整局不触发**——第 3 年末那 44M 本息是引擎在 `nextQuarter` 里自动结的（会进控制表 e-1 行，但 runner 没有对应的一步，讲解卡不会为它停）。其余 11 条讲解点在本局都会按序亮出来（含只落 1 步的 `q-8` 与 `q-15`）。要把长贷讲解留下，就把 `YEAR_INTENTS[4].longLoan` 写回 `true`，终局读数改成现金 26M/权益 121M。

草案的"第 2 年两条线"也作废：`productionSteps` 每季重复吐 `newLines[0]`（只数条数不推进到下标），声明两条只会得到两条同款线，第二条实测把第 3 年末关口压穿 14M。**因此本局 P2 只有资格没有产能**（`productRD.P2.completed === true`，一张 P2 单也选不到）——要把 P2 落点做出来，得先修 `productionSteps`，属 Task 4 收口（§10 第 9 条）。

意图只说"投多少广告、上不上线、开拓谁"，**不写**"选哪几张单、下几个 R1、哪条线开工"——那些归 decide。

回写里没变的两列也说明一下，免得下一个人以为是漏改：**研发**按草案（第 1 年启动 P2，Y1 内 4M、跨到第 2 年 Q2 满 6M 完成）；**现金垫**除第 3 年外都按草案，且实测它不咬人——把第 3 年的 8M 降到 4M，终局读数逐项不变（那一季的自救由 `estAutoOutlay` 主导，`cashPad` 只是加在它上面）。国内开拓从草案的"第 3 年起投"提前到"第 2 年起投"（`MARKET_DEVELOP_YEARS.domestic = 2`，Y3/Y4 投要第 5 年才 `available`，而订单池只读第 4 年 Q1 的 status）：按草案投法终局现金 5M/权益 120M，比**完全不投**（6M/122M）还差，改成 Y2+Y3 后是 8M/123M。

### 4.5 decide 的职责与不变式

每季度按序产出步骤，顺序对齐控制表行位（q-2→q-6→q-7→q-10→q-14→q-15→q-16）：

1. **选单**（`selectOrder`）：从 `availableOrders` 里按"**本年可承诺量**"筛（`decide.ts:30-45` 的 `commitableUnits`＝在手成品 + 白名单内各线到年底的折算完工量 − 已选未交），优先单价高、账期短，张数不超 `orderCap`。
   **（Task 9 按实现更正）**本条原文写的是"按'到期季 ≤ 本季 + 在手产能'筛"，那句**用词有误**：引擎的 `Order` 里根本没有交付期限字段，只有 `paymentPeriod`（账期，`src/types/enterprise.ts:211-220`），没有"到期季"可拿来比较；而 `availableOrders` 每次 `enterOrderMeeting` 都被整体重建（store:1791），未选的单不跨期存活——"到期"这一维在数据模型里不存在。按"本年可承诺量"落地就是它的原意：本年造不出来的量就是交不出，因为下一年池子换了、这张单也不再在了。
2. **下原料单**（`placeRawMaterialOrder`）：按 `PRODUCT_BOM` 与提前期倒推——P1 需 R1、P2 需 R1+R2，R1/R2 提前 1 季、R3/R4 提前 2 季；下单量 = 未来两季计划投料 − 在手库存 − 在途。
3. **开工/上线**（`startProduction` / `addProductionLine`；**转产 `convertProductionLine` 不进本期**，见 §7）：实现里开工的判据是三条——状态在 `PRODUCIBLE_STATUS` 白名单内（`running`/`idle`/`stopped`，`decide.ts:20-22`，用在 `:157`）、该线需要的料齐（同函数 `:162-166`）、`inProgressProducts === 0`。
   **（Task 9 按实现更正）**本条原文写的是"**只在本季有单要交时开工**"，这一条**控制者未采用**，所以已从规格删去：它与 §4.4 第 1 年"两条既有全自动线满产 P1"正面矛盾，而 §10 第 13 条的实测已经证明决策层拦不住产出（`running` 的线由引擎在 `nextQuarter` 里自动续产，加这道门只会让第 1 年空转、把投料与加工费照常照付）。取舍记在 §10 第 15 条。
4. **交货**（`deliverOrder`）：选单里尚未交付的，库存够即交（**Task 9 更正**：原文写"到期未交"，但"到期"那一维不存在，见第 1 条；实现是 `deliverySteps` 按 `selectedOrders` 数组序逐张扣库存，`decide.ts:179-194`）。
5. **自救**（`discountReceivable`）：现金低于垫下限且应收池够 7 的倍数时贴现，按 7:1。

**现金垫是动态量，不是常数**。本季现金下界（实现：`rescueSteps`，`decide.ts:305-307`）：

```
floor(y,q) = estAutoOutlay(s)      // 跨入下一季时引擎会自己扣的合计
           + ownSpend(steps, s)    // decide 本季自己发出去的手动支出
           + intent.cashPad
```

**（Task 9 按实现更正）**原式写成"该季引擎自动支出合计 + 当季到期长贷本息（仅第3年末）+ 当季到期短贷本息 + intent.cashPad"，两处失真：① 长贷本息与到期短贷本息**不是**并列在 floor 上的独立两项，它们已经在 `estAutoOutlay` 里按"跨入的那一季"结算——短贷用 `settleDueShortLoans(loans, nextAbs)`、长贷只在跨入第 1 季时走 `settleLongLoansAtYearEnd`（`decide.ts:203-236`）；② 漏了 `ownSpend` 整项：季初 `cash ≥ 只含引擎自扣项的下界`，并不代表走完税、广告、上线首付、加工费之后还在下界之上（这一条在 Task 5 的"修 3"里补上，写进 `rescueSteps` 的 `spent` 形参）。

`estAutoOutlay` 的枚举项与原文同族（料款、安装分期、维护、租金、长贷本息、行政、研发、加工费），两处口径按实现写清：**应付账款每季都计**，不是只在年末——引擎在下一季季初全额归还（store:2233 无条件读当前值、`:2245-2246` 记账、`:2781-2786` 计入实付净额；归还门排在总透支门之前），所以决策时刻的当前值就是下一季要还的数（`decide.ts:216-221`）；**安装分期按在建线数逐条计**，每条 `status === 'installing'` 的线在每次推进各扣一期 `purchasePrice / installationPeriod`（`decide.ts:225-230` 对 store:2401-2436），与"本季新建线付的那一期首付"不重叠——首付由 `ownSpend` 计。

`ownSpend`（`decide.ts:258-293`）覆盖的正是那些手动门：税（`payTaxes` 年初一次交清）、广告额、市场开拓与 ISO 各 1M、开工的加工费、新建线的首付、研发启动那 1M，以及**本季刚下的短提前期原料单**——R1/R2 提前 1 季，到货期恰是 `nextAbs`，而 `estAutoOutlay` 的 `arriving` 只扫季初已在途的单、看不见这一张（两不沾就会让 floor 虚低、少救一次）；R3/R4 提前 2 季，到货在下一季之后，由那时的 `estAutoOutlay` 接手。

之所以必须动态：**第 3 年末那道关口实测约 71M，而不是原写的"初始长贷 40M 在那里一次性到期"**。跨入第 4 年第 1 季的那一次推进要同时结掉：长贷 **44M**（40M 本金 + 10% 一年息，`drawnAbs = absQuarter(1,1)-4`、`termQuarters: 12`、每年末减 4、第三个年末归零，`settleLongLoansAtYearEnd` 见 `src/utils/rules.ts:46-62`）+ 第 3 年第 1 季那笔 20M 短贷到期的 **21M**（同一季界）+ 当季的设备维护费、小厂房租金与税金；而当年 `applyLongTermLoan` 会被"未还本余额已达上限40M"拒掉（余额在跨入第 4 年才归零），§4.4 的现金垫因此必须把这一整叠单独安排。本局靠第 2 年扩产能抬收入、第 3 年少资本开支、并把第 3 年 Q1/Q3 两笔短贷排在关口两侧过线；贴现那一侧在这一季是空转的（§10 第 10 条），若实测仍凑不齐，§9-5 的后备方案生效。

**硬不变式**：`decide` 产出的任何步骤序列，都不允许把现金压到 `floor` 之下；违反即视为决策层缺陷，不是剧本可容许的运气问题。

### 4.6 runner 状态机与撞门检测

`idle → playing ⇄ paused → blocked → finished`，外加 `exit`。

step 形状 `{ stepId, label, run, rule?, isPausePoint }`。逐季惰性展开：进入第 Y 年第 Q 季才调 `decide`，因为决策要读实时状态，而剧本只声明意图。

**撞门检测用双信号**：
- 结构性主信号——调用前后 `getState().state` **引用是否变化**。每条成功路径都返回新 `state` 对象，被拒路径只返回 `{ validationError }`，`state` 引用不动。
- 消息——非空 `validationError` 只用来取那句人话原因。

两者不一致（引用变了但仍报错）按"成功但有提示"处理并继续。这样不依赖每条门都记得写消息。

撞门即**停**，不静默跳步：面板显示「第 X 年第 Y 季 · <步骤名> 被拒：<原因>」，给三条出路——重试此步 / 跳过此步 / 退出演示。跳过只影响当季（下季由 decide 重算），不连锁。课堂上讲错比卡住更糟。

自动播放最快档 **300ms/步**，最慢 1200ms/步。这个数字不是手感调出来的：它保证相邻两次操作不会落进同一个 `Date.now()` 毫秒，避开 §3 那条核对盲区——老师若把演示局存档包导出去核对，不会印出一条并不存在的"账实不符"。**Task 7 真跑给它加了第二个理由，而且更硬**：`Date.now()` 还进业务主键（订货会订单 id `order-${Date.now()}-${i}`，store:1748；原料单 id 当时是 `order-${Date.now()}`、不带序号，store:1543），同毫秒的两次订货会会生成同 id 的订单，交货时一次标记两张却只扣一张的库存与应收，演示会在第 2 年第 4 季撞一次说不清的门（§10 第 7 条）。

**但这条下限只管得到 `play()`**（Task 7 审查更正，原先这里写成"任何绕过 UI 的批量驱动都必须自己保证每次操作落在不同毫秒"，那句不成立）：`step()` 与 `skipQuarter()` 是**同步批量**，一次调用就把整季的步走完，相邻两步常常落在同一个毫秒，300ms 根本拦不住它们；课堂上面板又可交互（§9-7），教师点一次「取消原料订单」就会碰到同 id 的连带删除。所以同毫秒碰撞的正解是**让 id 带序号**，不是靠时间间隔——原料单 id 本轮已在 store 侧补上序号（`order-${Date.now()}-${seq}`，与订货会订单 id 同写法）。**（Task 9 更正）**这一句原本还跟着"订货会那一侧本来就带 `-${i}`"，那句是**错的**、也与 §10 第 7 条自相矛盾：`-${i}` 是**每次会议内部**从 0 重新起算的序号，不是全局唯一键，所以两次订货会只要落在同一毫秒就会生成**同一组 id**（`order-<同一ms>-0`、`order-<同一ms>-1`…），`selectOrder` 按 id 搬运会搬错、`deliverOrder`（store:2059-2061）一次标记两张却只扣一张的库存与应收——**跨会议同毫秒仍撞、仍错数据**，根因修法是把年季放进 id（§10 第 7 条），本期不修。下限保留它本来的含义：播放时避开核对盲区的最小可行值。测试里则显式装时钟（`tests/demoRun.test.ts` 的 `withStepClock` 把毫秒每次推进 300ms、`withFrozenClock` 把毫秒钉死以复刻同毫秒碰撞）。

**restart（面板的「重新开始」）= 先 `exitDemo()` 再 `enterDemo()`**，不是"再调一次 start"。`enterDemo` 在 `demoMode === true` 时是幂等早退（store:551，Task 1 有测试钉着这条守卫），只调 `start()` 的"重开"实际是**对当前半年季重跑 `decideQuarter`**：年初段没有"本季已投过广告/已开过订货会"的判定，于是再扣 2M 广告（`advertisements` 跨年不清零，解锁张数按历年之和算，等于改写后三年的订单池）、订单池被整替（已选单的 id 全部失效），若在 Q3 中途按下还会再借一笔 20M 短贷。那属于数据损坏，不是"停住"。

**面板的两个读数分工（Task 8 照这个接）**：讲解卡读 `lastStep`（刚成功执行的那一步，它的 `rule`/`label` 就是该念的原文，§4.7），进度读 `queue.length`（本季还剩几步）。`advanceOne` 是**先弹出队列首位再执行**，所以讲解点自动停的那一刻 `queue[0]` 已经是下一步——面板若取 `queue[0].rule`，卡片会错一格。`start`/`restart`/`exit` 清空 `lastStep`。

撞门检测的相位收尾：被拒转 `blocked` 后，**重试成功要把相位拉回 `paused`**（只清 `blocked` 字段不行——`skipQuarter` 见 `blocked` 就早退，面板会出现"被拒但报错区已空"的死格）；`skipQuarter` 清 timer 后**只在当前相是 `playing` 时**把相位落回 `paused`（留在 `playing` 却没有 timer，`play()` 首行见 `playing` 早退，读数说"播放中"却一步都走不动）。**不能无条件落 `paused`**（Task 7 第 2 轮更正）：那句 `set` 原本排在循环的早退检查之前，于是将终局的 `finished` 与队列已空时刚置的 `blocked` 一起盖掉——前者让面板丢掉"已完成"读数（队列已空，`play()` 再也起不来），后者留下"报错区有文字、相位却说正常"。守卫在 `tests/demoRun.test.ts` 的 `skipQuarter 的相位` 那一组。

### 4.9 数据流（一次"下一季"）

```
老师点「跳到下一季」
  → runner 把当季剩余 step 依次执行（每步：清 validationError → 调 action → 比 state 引用）
  → 执行 nextQuarter()（引擎自动结算 q-1/2/4/5/7/8/10/11/15/16、跨年时 e-1/2/3/4/6）
  → autoSaveGame 被 demoMode 短路，localStorage 未写
  → runner 展开下一季 decide()，得到新一批 step，回到等待
```

## 5. 错误处理

| 情形 | 处理 |
|---|---|
| 某步撞门（时机不对/现金不足/余额达上限） | 转 `blocked`，显示年季 + 步骤名 + `validationError` 原文，停自动播放，三条出路 |
| `nextQuarter` 因当季透支被拒（`:2749`） | 同上——这正是第 3 年末最需要看清的一格，把缺口金额原样交给老师 |
| 讲解点引用的 section/item 不存在 | 面板退化显示步骤名不显示讲解卡；由 §6 第 4 组测试在 CI 拦住，不允许线上退化 |

## 10. 已知取舍与遗留

1. **runner 的成功判据是 `state` 引用比较**，属于结构性间接信号。将来若有人把某条 action 改成"就地 mutate `state` 对象后返回同引用"，runner 会误判为被拒。缓解：§6 第 2 组全速跑通会立刻抓到大面积 `blocked`；根除要靠 action 层给出显式返回值，本期不动 store 的 30 余个 action 签名。
2. **剧本与规则强耦合**：广告投放、市场维持、贷款上限任一处改动都可能让 §6 第 2 组变红。这是设计意图而非缺陷（规则改了演示就该重新对表），但要求后续维护者跟着改 `script.ts`，不能反过来放宽测试。
3. **decide 的启发式不保证最优**：取向已定为"只要流程完整、不断流"，因此不追求权益最大。某些参数下第 3 年末仍可能吃紧，此时按 §9-5 后备顺序处理。
4. **不做演示局进度保存**：退出即丢。**（最终审查修复波更正）**本条原写"老师若要留存演示结果，用导出控制表 CSV / 存档包（只读动作，演示中可用）"，那两件产物演示期**不可用**——它们的取数源是本机存档帧而不是演示局（§4.8 第 2 闸末段、第 20 条）。演示期真能留存的只有：`导出日志`（当前屏 `operationLogs`，即演示局自己那一本账，退出后就没有了）、`导出核对报告（txt）`/`（json）`（数据源是你导入的那份包，不是本机帧）、以及截图/录屏。
5. **既有缺口，本期只记录不修**：长贷本息与短贷本息在 `nextQuarter` 内无独立现金守卫，全靠 `:2748-2751` 那条"整季透支则拒绝推进"兜住——结果是季度推不过去而不是负现金，这个行为是对的，但提示语只说"请先贴现应收账款或申请贷款"，不区分是贷款到期造成的。演示会正好撞上这句话，届时按 §5 原样显示，不改文案。

Task 7（runner 落地 + 第一次真跑一整局）新增的遗留，编号接着往下：

6. **runner 在订货会之后补一次选单**（`selectStepsAfterMeeting`）。`decideQuarter` 是季初展开的，而订单池要 `enterOrderMeeting` 现场才生成（id 含 `Date.now()`，事前无法预知）——第一次真跑表现为"全年零选单、库存堆着、现金只出不进"，第 2 年初连 2M 广告都付不出。补的只是 `pickOrders` 这一个问题（谓词仍在 decide.ts 单源），**不重跑整季**：重跑会二次投广告、二次下单。代价是选单之后的投料/开工/交货/贴现四组仍是季初算的，看不见本季新选的订单（本季交不了新单，交货侧无影响）。

10. **`rescueSteps` 是"够不到 floor 就一分不贴"的开关式自救**（Task 5 收口项）：`for` 里只有 `cash + gain >= floor` 才返回，floor 高过应收池能救的上界时返回 `[]`，于是要贴 12M 救 4M 的洞时它一次都不贴，缺口原样交给 `nextQuarter` 的透支门。第 3 年末那一道（44M + 21M）正好是最需要"贴满"的时候，§9-5 第 1 档的"先加大贴现"在这一季是空转——本局是靠短贷过gate 的，不是靠贴现。最小改法：把循环换成"够不到 floor 就按 `max` 贴一次"（仍是 7 的倍数，保守方向不变）。
